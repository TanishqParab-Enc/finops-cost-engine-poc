# E-commerce Platform (`ecommerce-platform`)

A production-shaped AWS online-retail workload, built as a **second, fully
independent stack** under the same Shift-Left FinOps governance engine that
already governs `web-platform`.

Its purpose is to demonstrate that the governance system is **stack-agnostic**:
registering a Terraform root in `config/finops-stacks.yml` is the entire
integration. There is no cost, pricing, policy, approval or reporting logic
anywhere in this directory.

```
        ONE SHARED FINOPS GOVERNANCE ENGINE
                      │
        ┌─────────────┴─────────────┐
        │                           │
  web-platform              ecommerce-platform
  (existing workload)       (this workload)
  own Terraform root        own Terraform root
  own remote state          own remote state
```

## Request and data flow

```
Customer
   │
   ▼
Route 53  (shop.<zone>)
   │
   ▼
CloudFront ──────────── /assets/* ────────────▶ S3 (product assets)
   │  default behaviour
   ▼
Application Load Balancer   (public subnets)
   │  HTTP :8080
   ▼
Storefront Auto Scaling group   (private app subnets)
   ├──▶ RDS PostgreSQL          (private data subnets)
   ├──▶ ElastiCache Redis       (private data subnets)
   ├──▶ S3  (product assets)
   ├──▶ SQS (order events)          ── send only
   └──▶ Secrets Manager (runtime config)

SQS order queue
   │  poll
   ▼
Worker Auto Scaling group      (private app subnets)
   ├──▶ RDS PostgreSQL
   ├──▶ S3  (fulfilment artefacts)
   └──▶ SQS dead-letter queue   ── on repeated failure

CloudWatch  ── logs + alarms across ALB, EC2, RDS, SQS and ElastiCache
```

The checkout path never blocks on fulfilment: the storefront writes an order
event to SQS and returns. Workers drain the queue asynchronously and scale on
**queue backlog**, not CPU, because a worker waiting on I/O looks idle.

## Network design

Three subnet tiers per AZ, across two AZs:

| Tier | Contents | Internet route |
|---|---|---|
| Public | ALB, NAT gateway | Internet Gateway |
| Application | storefront + worker instances | via NAT gateway |
| Data | RDS, ElastiCache | **none** |

The data tier has no default route in either direction. Security groups form a
strict chain — `internet → alb → app → data` — and the only rule using
`0.0.0.0/0` for ingress is public HTTP on the ALB. Workers accept **no**
inbound traffic at all.

## Modules

| Module | Responsibility |
|---|---|
| `networking` | VPC, 3× subnet tiers, IGW, NAT, route tables, 5 security groups |
| `edge` | CloudFront (dual origin: ALB + S3 via OAC), Route 53 zone and alias |
| `alb` | Application Load Balancer, target group, HTTP listener |
| `app_compute` | Storefront launch template, ASG, CPU target-tracking policy |
| `worker_compute` | Worker launch template, ASG, SQS-backlog target-tracking policy |
| `database` | RDS PostgreSQL, subnet group, parameter group |
| `cache` | ElastiCache Redis replication group and subnet group |
| `storage` | S3 product assets: versioning, SSE, lifecycle, TLS-only policy |
| `messaging` | SQS order queue, dead-letter queue, redrive, TLS-only policy |
| `secrets` | Secrets Manager entry for runtime configuration |
| `monitoring` | 2 log groups, 6 alarms (CPU, 5xx, DB CPU, backlog, DLQ, evictions) |
| `iam` | Separate least-privilege roles and instance profiles per tier |

## Security posture

- **Separate roles per tier.** The storefront may `sqs:SendMessage` but never
  receive; the worker may receive and delete but never send. Neither can reach
  the other tier's log group.
- **No `AdministratorAccess`**, no wildcard resource ARNs except the RDS-managed
  secret prefix (`rds!*`), scoped to this account and region.
- **No hard-coded credentials.** The database master password is generated and
  rotated by RDS (`manage_master_user_password`), so it never enters Terraform
  state. The application signing key is generated by `random_password`.
- **IMDSv2 required** on both tiers, blocking the SSRF-to-credential-theft path.
- **Encryption everywhere practical**: EBS, RDS storage, S3 (SSE-S3 + bucket
  keys), SQS (SSE), Redis at-rest and in-transit.
- **S3 public access fully blocked**, plus a bucket policy denying any
  non-TLS request.

## Cost levers

The values that materially move the monthly bill are parameterised in
`terraform.tfvars` and echoed in the `cost_levers` output so a reviewer can see
which ones a change touched:

`app_instance_type`, `app_desired_capacity`, `worker_instance_type`,
`worker_desired_capacity`, `db_instance_class`, `db_allocated_storage`,
`db_multi_az`, `cache_node_type`, `cache_node_count`, `nat_gateway_count`,
`enable_cdn`, `cdn_price_class`.

`infracost-usage.yml` documents the consumption assumptions for S3, CloudFront,
SQS and CloudWatch, which Terraform alone cannot price. They are assumptions,
not measurements — the gate flags anything priced this way as `usage_based`.

## FinOps integration

Registered in `config/finops-stacks.yml` as:

```yaml
ecommerce-platform:
  terraform_dir: terraform/workloads/ecommerce-platform
  state_key: finops-poc/dev/ecommerce-platform/terraform.tfstate
  deployable: false
  usage_file: terraform/workloads/ecommerce-platform/infracost-usage.yml
```

That registration is the whole integration. The shared pipeline then detects
changes, plans, prices with Infracost, applies the existing threshold, requires
approval when exceeded, and mints the cost lock — identically to `web-platform`.

`deployable: false` is deliberate: the Dev deploy role has not yet been granted
ElastiCache, SQS or Secrets Manager write access, so an apply would fail
partway through. Pricing, gating and reporting are unaffected; flip it to `true`
once that policy is extended and reviewed.

Greenfield and brownfield need no special handling here. The gate establishes
the baseline from this stack's own remote state: absent or empty state prices as
a $0 baseline, existing state prices as the currently deployed cost.

## Local use

```bash
cd terraform/workloads/ecommerce-platform

terraform fmt -recursive
terraform init -backend=false     # no state, for validation only
terraform validate
```

The backend is intentionally empty in `versions.tf`; the pipeline supplies
bucket and key at `init` time from the registry, so this workload can never
share state with another.
